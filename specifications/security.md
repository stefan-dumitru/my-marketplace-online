# Security Requirements

The project-wide default posture (validate input, no secrets in code, default-deny authz) is in
[../CLAUDE.md](../CLAUDE.md) and applies regardless of what's filled in below. This file is for
requirements specific to *this app* — its data sensitivity, its auth model, its compliance scope.

## Data Sensitivity

- Most sensitive data this app stores: buyer/seller PII (name, email, shipping address) and
  password hashes. No payment data — checkout is simulated, no card/bank details ever collected
  (see `functional.md` > Non-Goals).
- Regulatory scope: no formal compliance target (not GDPR/HIPAA/PCI-DSS scoped as a legal
  requirement — this is a portfolio project), but designed with GDPR-style data handling as a
  practice: account deletion anonymizes personal data rather than just deactivating the account
  (see `data-model.md` > Data Retention).

## Authentication

- Method: email/password, in-app sign-up (no magic link, no OAuth provider).
- Session handling: server-side session, httpOnly cookie. Exact expiry/refresh policy:
  **[TODO]** — not decided; pick something reasonable (e.g. a sliding expiry) during the auth
  feature's Plan Mode.
- MFA required: none for v1.
- External identity provider: N/A — this app has no external identity source.

## Authorization

- Model: role-based (`guest` / `buyer` / `seller` / `admin`, from `functional.md` > User Roles)
  layered with ownership checks — a buyer only acts on their own cart/orders/reviews/addresses;
  a seller only acts on their own products and the orders that contain them.
- Enforcement pattern *(assumed default — adjust if needed)*: FastAPI dependency-injected guards
  (e.g. `require_buyer`, `require_seller_owner(product_id)`, `require_admin`) applied per route,
  so every endpoint enforces authorization the same way rather than each handler rolling its own
  check. Given the biggest threat below is cross-role data leakage, consistency here matters more
  than the exact mechanism.

## Data Protection

- Encryption at rest *(assumed default)*: relies on the hosting provider's defaults — Railway's
  managed Postgres and Cloudflare R2 both encrypt at rest — no additional application-level
  column encryption for v1, since there's no payment/health data to justify it.
- Transit security: HTTPS baseline only (per `CLAUDE.md`); no additional mTLS/VPN — single app,
  no internal service-to-service traffic to protect.
- Fields requiring extra protection: `password_hash` (bcrypt/argon2, never logged, see
  `CLAUDE.md` > Security Baseline); addresses and other PII are never written to application logs
  — log a user ID, not the PII itself (see Audit / Logging below).

## File Upload Handling

Applies to product image uploads.

- Allowed file types and max size: JPEG, PNG, WebP; 5MB max per file.
- Storage location and naming convention: Cloudflare R2 (S3-compatible). The stored object key is
  generated by the app (e.g. a UUID-based path), never derived from the uploaded filename.
  Authorization (does this seller own the product being uploaded to) is checked before the file
  is written, not after — per `CLAUDE.md` > Security Baseline, restated here because it's the
  rule this feature must not skip.
- DB storage: `ProductImage.storage_key` stores the R2 object key (not a full URL); the app
  resolves it against a configured bucket/base URL at read time.
- Original filename: retained as display metadata only, in `ProductImage.original_filename` —
  never used to derive the stored path.

## Threat Model (lightweight)

- Biggest realistic threat: cross-role data leakage — a seller or buyer seeing or modifying
  another seller's/buyer's data because an authorization check was missed. Most likely bug class
  given three roles with overlapping data (a seller is also a buyer; orders are jointly owned by
  a buyer and a seller).
- Explicitly out of scope for launch: DDoS/rate-limit hardening and payment-security concerns
  (moot — checkout is simulated, see `functional.md` > Non-Goals). Accepted risk for a
  portfolio-scale deployment.

## Audit / Logging

- Actions that must be logged: order status transitions (`OrderStatusHistory`), product
  moderation actions (`ProductModerationLog`), admin actions on sellers — approve/reject/suspend/
  reinstate (`SellerActionLog`), login attempts success/failure (`LoginAttempt`). See
  `data-model.md` > Change Auditing for the entities.
- Log retention: indefinite for v1, consistent with the "no retention policy" decision in
  `data-model.md` > Data Retention.
- Bulk-operation per-record logging: N/A — no bulk operations in this app.
